The [privacy policy](/privacy) makes claims. This page is how you check them yourself — three tests, a few minutes, no trust required. If any of them ever fails, the claims are false and we want to know: [snippets.support@gmail.com](mailto:snippets.support@gmail.com).

The claim: while you're signed out, your entries never leave this device — writing needs no network at all.

## Test 3 — The list your browser enforces

The claim: this app **cannot** send data anywhere you haven't seen above — not by policy, but because your browser refuses to let it.

Every page we serve carries a `Content-Security-Policy` header. Its `connect-src` line names every web address this app is allowed to contact; the browser blocks anything else before it leaves. Check the header from any terminal:

```
curl -sI https://www.snippets.ink | grep -i content-security
```

Or paste `snippets.ink` into [securityheaders.com](https://securityheaders.com). The addresses you find in `connect-src` are the ones from Test 2 — the whole list, enforced.

**What this test can and cannot prove.** It proves where data can go. It cannot prove the code itself is honest — a web app's code arrives fresh from the server on each visit, so you are trusting that delivery <<the whole point of the verify page is so that we could relax warnings like 'one honest catch - you depend on our code working the way we said it does' -- which means that this sentence feels very undermining. do we even need it, or could we change anything to obsolesce this sentence? i suppose same goes for the sentence after this ie, the whole paragraph>>. Tests 1 and 2 narrow the question to what the code you were served actually does; the deeper protection is that any altered code would run in your own browser, open to inspection — not a silent query on a server you can't see.
